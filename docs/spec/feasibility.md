# Feasibility

How each feature can be built, what it depends on, and where the risks are.

Part of the product spec. First written as draft 13 of the product spec, 15 November 2026.

## Can it be done? Feature by feature

| Feature | Verdict | How | Caveats |
| --- | --- | --- | --- |
| **Menu bar app, timers, sounds, notifications** | Yes | SwiftUI `MenuBarExtra` for the status item and panel, `UserNotifications` for alerts, bundled sound files. | None. This is standard platform work. |
| **History and charts** | Yes | SwiftData for storage, Swift Charts for week and month views. | None. |
| **List Claude Code sessions** | Yes | Claude Code hooks. A small hook script reports session start, prompt, stop and "needs attention" events to the app. Each event carries the session id, the transcript file path and the working directory. "Needs attention" is a permission request, or a notification of the type `permission_prompt`. A stop alone is not "finished": it lists the background work still running, and a subagent, a workflow or a teammate keeps the session working. Transcripts are local JSONL files, so titles and last activity can be read from disk. That was not tried in phase 0. | After a denied permission or an Esc no `Stop` comes. After an Esc nothing comes at all, and after a denial only an `idle_prompt` notification, about three minutes after the prompt, which the app does not take as the end of a turn ([the event orders](../spikes/claude-hook.md#event-orders-for-the-basic-cases)). So the app needs a fallback to leave "working" or "waiting". The app installs hook entries into your Claude settings file. It must do this carefully and reversibly. That file can be a symlink shared by several profiles, and only a file that comes back byte for byte from a two-space JSON round trip can be given back unchanged. |
| **Three Claude accounts** | Yes, with caveats | Verified on the maintainer's Mac: each account has its own Claude Code profile folder. The app watches all of them and labels sessions by profile. Each event names its profile: `CLAUDE_CONFIG_DIR` when it is set, otherwise the part of the transcript path before `/projects/`. | The hook is installed once per settings file. Several profiles can share one file through a symlink, as every profile on the maintainer's Mac does, and one install then reaches all of them. Chats in claude.ai or the desktop app have no public listing API, so only Claude Code sessions on this Mac are covered. |
| **Codex sessions** | Yes, with caveats | Codex CLI also writes local session files and supports a notify command. Same pattern as Claude. | Not in use on the maintainer's Mac yet. This adapter is built when it is first needed, and nothing else depends on it. |
| **Focus Terminal and iTerm2** | Yes | The hook script runs inside the terminal, as a child of the `claude` process, so it can read which app and which tab it is in. It has no tty of its own, so the tab's tty is the one of its parent. iTerm2's handle is the UUID after the colon in `ITERM_SESSION_ID`, and Terminal's is the tty. The app then selects that exact tab through AppleScript. In Terminal each tab is its own AppleScript window, so the app first checks that the session's `claude` process still holds the tty, because a tty is reused at once, and then brings that window to the front. Proven 120 of 120 per app in phase 0, from a script and with plain shell tabs. | macOS asks once for permission to control each terminal app. The permission belongs to the app that sends the events, so the Dev and the Release build each ask. A window on another Space or in full screen comes forward with a visible jump. Nothing comes forward while the screen is locked. |
| **Focus VS Code and Cursor** | Yes, with caveats | The hook names the editor by its bundle id. `TERM_PROGRAM` is `vscode` in both, so it names neither. `open -b <bundle id> <folder>` asks LaunchServices to open the session's folder in that editor, which brings forward the window that has exactly that folder open. It needs no AppleScript, which neither editor has, no shell command on PATH and no permission. Proven 10 of 10 per editor in phase 0, from a script. The `code` and `cursor` commands were not tested. | Decided: window-level focus is enough. Selecting the exact integrated terminal tab would need a companion extension, which is not planned. The app knows the session's working folder, not the window's. Any other folder, such as a subfolder of the window's, opens a new window, so the app then only brings the editor forward, which may show another window. A remote or container session cannot be focused. With `window.openFoldersInNewWindow` set to `"off"`, a folder no window has replaces the folder of the user's window. These three are reasoned from VS Code's source, not measured. `open -b` is expected to start an editor that is not running. The spike never saw it, so the app checks first. |
| **Jira: pick issues, log time** | Yes | Jira Cloud REST API. Search with JQL for your issues, then post a worklog to the issue with seconds spent, start time and comment. The same API updates and deletes a worklog, so hours can be corrected after sending. Sign in per site with email and API token. | The site must have time tracking enabled. If an organization logs time through Tempo, that is a separate API. Self-hosted Jira uses a different token type. Correcting a sent worklog needs the project permission to edit your own worklogs. |
| **Google calendars from company accounts** | Yes, with caveats | Verified on the maintainer's Mac with a company Google account: once a Google account is added in macOS System Settings with Calendars switched on, its meetings land in the calendar the Mac already keeps. The app reads every calendar from there through EventKit with one permission prompt. No Google sign-in code in the app. | macOS fetches a Google account every 15 minutes by default, so a change made in the last few minutes can be missing. Out of office arrives as a timed entry and nothing is proven to mark it, so the app goes by its name, from a short list you can edit, and phase 5 checks whether macOS passes along a marker too. Another company's admin can block this route. Fallback is the Google Calendar API with OAuth, which needs a Google Cloud project and may need admin approval. |
| **Sync Mac and iPhone through Apple ID** | Yes, with caveats | SwiftData with CloudKit private database. Data lives in your own iCloud, no server to run. | Needs the paid Apple Developer Program. CloudKit restricts the data model (no unique constraints, optional relationships, additive-only changes after go-live). Mac sync has known quirks that we design around. |
| **iPhone app** | Yes | Second SwiftUI target reusing the shared package. Live Activity for the countdown. | Sessions and terminal focus stay Mac-only. The phone can show session state read-only if we sync it. |
| **insight-flow** | Yes | Verified in the insight-flow repository: `insight-flow current` prints JSON with the id, title and status of the current task, and each project has one current task. The app detects repos with `taskflow.config.json`, asks the CLI and watches `.taskflow-activity.jsonl` for changes. | insight-flow ships its own alert sounds for an idle agent and for a permission prompt, so alerts need a per-project switch to avoid doubling. |
| **Installable by other people** | Yes, with caveats | Decided: free, open source, no App Store for now. Sign the app with a Developer ID certificate, have Apple notarize it, and offer it on the project page as a download that updates itself through the Sparkle framework. iCloud sync works in such a build too, and every user keeps their data in their own iCloud, so there is still no server to run. | Needs the paid Apple Developer Program even though the app is free. Without the App Store, the iPhone app reaches other people only through a TestFlight link, where every build stops working after 90 days. |
| **Mac App Store release** | Not for this app | App Store apps must be sandboxed. A sandboxed app cannot read other tools' session files or script terminals freely. | Run it from Xcode yourself. For other people, sign and notarize it as a direct download, which is how most developer tools for the Mac are shipped. |

### How a session gets linked to its terminal

1.  You start `claude` in any terminal.
2.  The SessionStart hook runs a tiny script as a child of the `claude` process. It has no tty of its own, so it reads the tab from its parent.
3.  The script sends the app: session id, folder, account (the profile folder), terminal app, tab identifier, and the `claude` process id, because a tty is reused at once. VS Code and Cursor have no tab identifier, and their terminal app is the editor's bundle id.
4.  Later hooks update the state: working, finished, waiting for permission. "Finished" needs a stop whose background work holds no subagent, workflow or teammate, and after a denied permission or an Esc no stop comes ([the event orders](../spikes/claude-hook.md#event-orders-for-the-basic-cases)).
5.  Focus button: in Terminal and iTerm2 the app tells that terminal app to select that tab, after checking in Terminal that the `claude` process still holds the tty. In VS Code and Cursor it asks LaunchServices to open the `cwd` of the session's first `SessionStart` in that editor, or only brings the editor forward. No Apple event goes to the editor.

No screen scraping, no accessibility tricks. The hook is the only moving part. Phase 0 needed neither Accessibility nor Screen Recording.

### Biggest technical risks

- **Terminal focus reliability** across four terminal hosts. Mitigation: prove it in a phase 0 spike before anything else is built on it. Retired in phase 0 for Terminal and iTerm2, and for VS Code and Cursor when the session's folder is exactly the window's folder. What remains: the focus sent from the menu bar app and from a signed, hardened build, the Automation permission asked by the app itself, the editors' subfolder case, remote and container sessions, activate only (bringing an editor forward without a folder), and the editor case end to end.
- **CloudKit sync on Mac.** Mitigation: add sync late, on a stable data model, and design the model for CloudKit from day one.
- **Hook formats change** as Claude Code and Codex evolve. Mitigation: one small adapter per tool, tolerant parsing. Borne out in phase 0: since Claude Code 2.1.302 subagents run in the background by default, which changes how the end of a session's turn looks.
- **Company restrictions** on Jira tokens or calendar access. Mitigation: both integrations are optional and the app is complete without them.
- **Other people's setups** differ: other terminals, agents and Jira flavors. Mitigation: one adapter per terminal and per agent behind a common interface, added when someone needs it.
